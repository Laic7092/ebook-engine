# 设计

README 说“只有排版是核心”。本文把这个论证展开：为什么边界要这样切、
哪些不变量必须成立、以及这些选择换来了什么可测试性。

---

## 1. 分层与依赖方向

```
ebook-format ──> ebook-ir <── ebook-layout <── ebook-font
                       ^
                       └── ebook-render <── ebook-raster
                       └── ebook-web / ebook-cli
```

依赖只指向 `ebook-ir`，没有反向调用：

- `format` 解容器、解析 XHTML/CSS、做级联，产出**已计算样式**的 `StyledDoc`。
- `layout` 只认 `StyledDoc`、`LayoutEnv`、`PageConstraint`，产出 `LayoutResult`。
- `render` 只认 `&LayoutResult`，把 op 画到 `Surface`。
- `font` 是入参：`FontBook` 同时提供 `TextMeasurer` 与 `Resources`。
- `web` / `cli` 是组装层：读字节、选适配器、注入字体、调用排版与渲染。

没有 trait object 反向调用排版层。`Surface` 是渲染层的出口，`TextMeasurer`
与 `ResourceView` 是排版层的入口；两者都由组装层实现或注入。

### 为什么级联在格式层

排版只需要“计算后的值”。把选择器、继承、`!important`、层叠顺序都留在格式层，
排版层就永远看不到 CSS 语法，也不会在排版过程中重新求值样式。代价是
`StyledDoc` 必须携带完整的 `ComputedStyle`；回报是排版输入可以被手工构造，
随机文档测试不需要真实 HTML。

### 为什么字体在格式层之外、排版之内作为入参

字体 fallback 链因平台而异。一旦排版层自己去“找字体”，同一本书在不同平台
会量出不同行宽，分页、书签、跨端同步全部失效。这是正确性问题，不是性能问题。

因此：

- `FontBook` 由宿主创建并注入。
- 排版层只调用 `TextMeasurer`，不读字体文件、不写缓存。
- native 与 wasm 用同一份字体字节，度量与光栅化来自同一个 `FontBook`。

## 2. 不变量清单

以下不变量由 `crates/ebook-layout/tests/{invariants,properties,text_layout,pagination}.rs`
与 `xtask` 的 golden/pixel/parity/contract 共同覆盖。改排版时先看这张表。

### 2.1 页与 op 的覆盖关系

1. `pages[i].index == i`。
2. `pages[0].ops.start == 0`；后一页的 `ops.start` 等于前一页 `start + len`。
3. `pages[0].lines.start == 0`；行切片同样连续。
4. 所有页的 op 并集恰好覆盖 `display.ops`，行并集恰好覆盖 `runs.lines`。
5. 每页至少有一行；空文档可以没有页。
6. `page.lines` 里的每一行都落在 `[origin.y, origin.y + size.h]` 内（容差 1e-3）。
7. 页 `origin.x == 0`；`origin.y` 单调不减。
8. 行按 `rect.y` 单调不减。
9. 行的 `src.start` 单调不减（源文顺序）。

### 2.2 坐标与尺寸

10. 所有 op 坐标是**排版流坐标**，不是页面内坐标。
11. `Page.origin` 只由分页器写；改分页只移动 origin。
12. `Page.size` 是内容区尺寸，`Page.inset` 是页边距；
    `box_size()` = `size + inset`。
13. `content_size` 每个轴至少 `1.0`，极小页面不会除零或产生负尺寸。
14. 行盒不会因为负 margin 跑到页外；越界时宁可裁掉视觉，也不移动分页基线。

### 2.3 确定性与编解码

15. 同一个 `(StyledDoc, LayoutEnv, PageConstraint)` 重复排版逐字节相同。
16. `codec::to_bytes(layout(...))` 重复调用逐字节相同。
17. `decode(to_bytes(ir)) == ir`；再编码仍然是同一串字节。
18. 所有公开集合的遍历顺序固定：`Vec` / 固定数组，禁止 `HashMap` / `HashSet`。
19. 浮点运算顺序固定；不使用并行归约、不依赖迭代器实现细节以外的顺序。

### 2.4 边界与错误

20. `layout` 是全函数：空文档、极小页面、极深嵌套都返回可序列化结果。
21. 越界查询返回 `None`，不 panic：`page`、`page_of_line`、`line_at`、`anchor_at`。
22. span 切片与节点索引是信任调用方：越界 panic 属于调用方违约。
23. 渲染不存在的页返回 `NoSuchPage`，不绘制半页。
24. 缺字产 `FontMissing`，不猜字形；图片尺寸未知产 `ImagePending`，不猜尺寸。
25. `truncated == true` 时 1–14 仍然成立：截断只保留前缀，不留悬空 op/行/字形区间。
26. 只有一行、且该行连同比页内起点偏移都装不进内容区时，允许它溢出页面；
    其它任何情况下行都不越界（`tests/fuzz.rs` 把这条写成了断言）。

> 已知缺陷（1.4）：整行只有行内图片时，`LineBox.src` 从 0 算起（占位字符
> `U+FFFC` 按 3 字节计），不指向真实原文。选区会跳过这类行；修复需要改
> `flow` 的源区间计算。`tests/fuzz.rs` 暂时把 `Image` 行从 src 单调检查里排除。

## 3. 为什么 `DisplayList` 禁止 `HashMap` / `HashSet`

IR 是 native 与 wasm 之间的**字节契约**。`postcard` 按字段声明顺序编码
`Vec`，而 `HashMap` 的迭代顺序取决于哈希种子和容量历史：

- 同样内容的两个 `HashMap`，插入顺序不同，序列化字节就可能不同。
- 跨进程、跨平台、跨编译器版本，哈希实现可能不同。
- golden 与 parity 都要求逐字节相同，任何迭代顺序抖动都会变成假失败。
- 缓存键是 IR 字节的哈希；顺序抖动会让缓存永远不命中。

所以 IR 里只允许：

- `Vec`：插入顺序即语义顺序（页、op、行、dirty 块）。
- 固定数组：字体栈、字体名、边的四方向。
- 需要按 key 查找时，用排序后的 `Vec` + 二分，或者直接用下标（`NodeId`）。

这条禁令不是风格问题，是“字节流必须确定”的直接推论。`LayoutResult` /
`DisplayList` 里一旦出现哈希容器，parity 与 golden 就不再是可测事实。

## 4. 为什么 op 坐标是排版流坐标

分页会移动内容：今天第 3 页的第一行，改字号后可能落到第 4 页。如果 op 存的是
页面内坐标，每次重排都要重写所有后续 op 的坐标，渲染层与排版层就会出现两套
“页面偏移”逻辑。

流坐标把这两个概念拆开：

- 排版层在一条连续流里排所有内容，op 只记录“在流里的位置”。
- 分页器决定每页从流的哪个 `y` 开始，写进 `Page.origin`。
- 渲染时只做一次平移：`paint()` 把 `op - (origin - inset)` 交给后端。

于是：

- 改分页只改 `Page.origin` 和切片边界，一个 op 都不用重写。
- “渲染层不改坐标”不是纪律，而是数据结构允许它只做一次平移。
- 同一份 IR 可以被任意后端按页渲染，后端不需要知道分页算法。
- 页内坐标只在 `paint()` 里出现一次，SVG / 光栅 / Canvas 不会各自实现一套。

`Page.inset` 也参与这次平移：内容区坐标加上页边距，才落到页面盒坐标。

## 5. 分页为什么在排版层

断行决定分页，分页又反过来影响孤行寡行与段落切分。如果把分页放到渲染层：

- 孤行寡行需要回退断点，渲染层必须理解块结构。
- 强制分页会改变后续页的 `origin`，渲染层必须能改排版结果。
- 选区与 CFI 依赖 `RunMap`，页边界必须和行边界一起结算。

当前算法：

1. 把行与块级 op 展平成 `Unit` 序列，每个 unit 有 `y`、`h`、块号、行号、
   `orphans`、`widows`、`break-before/after`。
2. 从当前页顶开始，找最满的断点。
3. `resolve` 按约束往回退；退到段首仍不满足，就整段推到下一页。
4. 约束冲突时退回最满断点。宁可难看，也不产生空页。
5. 页首 `origin.y` 夹到 `上一页 origin + 1.0`，保证页序单调。

分页结果是 `PageStart` 列表；`PageBuilder` 再把连续的 op/行切成 `Span`。
所以页是切片，不是过滤。

## 6. native / wasm parity 为什么可测

可测的前提是排版层没有平台相关的隐藏输入：

- 不碰 I/O：字体、图片尺寸、页面约束都是入参。
- 不持全局可变状态：没有字体库单例、没有 `thread_local` 缓存。
- 不取时钟、随机：没有时间戳、没有随机种子。
- 不出现 `#[cfg(target_*)]`：同一份源码编到 native 与 wasm。

在这个前提下，`xtask parity` 用同一份 `fixtures/demo.txt`：

1. native 直接 `layout` 得到 IR 字节。
2. wasm 侧通过 wasm-bindgen 调同一个 `layout` 得到 IR 字节。
3. 比较两串字节。

浮点是 IEEE-754 单精度，postcard 是固定布局，`Vec` 顺序固定，所以只要输入相同，
输出就应当逐字节相同。任何差异都说明有隐藏状态、平台分支或顺序抖动——
这正是这条测试要抓的东西。

`xtask contract` 是另一条独立防线：JS 手写解码器把 golden IR 解出来再编回去，
要求逐字节还原。它抓的是“Rust 结构体改了，JS 忘了改”，与 parity 抓的平台差异
不是同一类问题。

## 7. 不确定性必须显式

排版层不能“顺手猜一个值”。当前把不确定性分成三类：

| 不确定性 | IR 表现 | 宿主动作 |
|---|---|---|
| 字体缺字 | `Op::Unresolved{FontMissing}` + `DirtyBlock` | 换字体/回退/标记缺字 |
| 图片尺寸未加载 | 占位盒 + `ImagePending` + `DirtyBlock` | 带尺寸重排 |
| 尺寸依赖内容 | 占位 + `SizeFromContent` | 提供尺寸后重排 |

渲染层看到 `Unresolved` 只画虚线框，不补全内容。这样分页结果不依赖加载时机，
纯函数性成立，书签不会因为图片晚到而跳页。

---

## 8. 渲染层为什么只读

`Renderer::render` 接收 `&LayoutResult`，类型上就拿不到可变 IR。渲染层只能：

- 按页取 `Page.ops` 切片；
- 按 `GlyphRun.glyphs` 取字形切片；
- 通过 `Resources` 取字形位图或图片；
- 把 op 画到 `Surface`。

它不能改坐标、不能重新断行、不能补全未知尺寸。否则就会出现第二套排版逻辑，
golden test 失去意义，跨端一致性也无法证明。

光栅后端的“整数混合”与 SVG 后端的“可读预览”是替代关系，不是备份关系：
同一份 IR 可以用任意后端画，后端之间不共享布局逻辑。SVG 只便于人眼检查，
字形位置直接来自 `GlyphRun.text`，不复现 kerning/bidi，也不作为几何参考——
几何一致性用 RGBA 逐字节比对。

## 9. wasm 边界

`ebook-web` 只做三件事：把字节交给格式层、把 IR 字节交给 JS、把字体注册进
`FontBook`。IR 是唯一的数据契约：

- header `EBIR` + major/minor 固定 8 字节；
- body 是 postcard 位置编码；
- JS 解码器手写，字段顺序必须与 Rust 完全一致；
- `web/encode.js` 只用于 contract 的“解出来再编回去”，不参与阅读器主路径。

`web/reader.js` 只按 `GlyphRun.text` 画文本，按 `Page.origin/inset` 平移画布；
它不解释 CSS，也不重新断行。字体描述由 `eb_font_desc` 从 `FontBook` 取出，
交给 canvas 的 `font` 字符串，保证量出来的和画出来的用同一份字体。
`web/app.js` 负责书架/阅读页路由与导入，`web/library.js` 渲染书架，
`web/db.js` 封装 IndexedDB（不可用时退化成内存），TXT 的编码检测在
`web/text.js`，分章仍在 `ebook-format::txt::TxtReader`。界面是移动优先的
响应式布局：阅读页用实际可视区域作为排版约束，手机用底部面板，桌面用侧边抽屉，
移动端工具栏在阅读时自动隐藏，轻点页面显示或收起；工具栏是覆盖层，显隐不会改变排版约束或触发重排。

## 10. 两遍式：先断行，再分页

排版层内部只有两个阶段，中间只传一份扁平的 item 流：

```
StyledDoc ──flow──> [Item::Line | Item::Op] ──paginate──> Page[] + Span 切片
             断行                       分页
```

**第一遍（`flow`）：盒树 + 断行。** 这一遍只关心宽度：展开块/行内盒、整形文本、
按 UAX #14 找断点、结算两端对齐与行高，产出行盒（`y` 已经定下）与块级 op。
每个 item 带 `block`、`order`、`len`、`orphans`、`widows`、`force`，供第二遍决定
断点，但这些字段不进 IR。

**第二遍（`paginate`）：页起点 + 切片。** 这一遍只关心高度：把 item 映射成
`Unit`，从当前页顶贪心找最满断点，再按 `break-before/after` 与孤行寡行往回退；
退不动就退回最满断点。结果是一串 `PageStart { unit, y }`，`PageBuilder` 再把连续
的 op/行切成 `Span`。

为什么不合成一遍：

- 宽度与高度的输入是分开的。页面只改高度时，断行结果完全不变，只要重新分页。
- 孤行寡行需要**回退**断点，而回退只能在“已经知道自己有哪些行”之后做；一边断行
  一边分页就把回退变成了改行。
- 第一遍是纯函数，第二遍只需要 item 的 `y/h/block` 摘要。两遍之间没有回调，
  也没有“分页器回头让断行器重排一段”的隐式循环。
- 两遍都结束后才做产出侧限额（`max_pages` / `max_lines`）：截断只能发生在
  “已经有了合法前缀”的位置，否则页覆盖与行不越界就不再成立。

代价是 item 流会多占一份内存（每个 item 一条记录，不含字形与文本本体）。
对于电子书章节这个量级，换来的“改页高不重排文字”与“限额可截断”更值。

## 11. 缓存键 = 输入指纹

`ebook-cache` 的键不是“文档 id + 版本号”，而是**把所有排版输入哈希一遍**：

- 文档结构：节点数、每个节点的 `kind` / 全部 `ComputedStyle` 字段 / `parent` /
  `first_child` / `child_len` / 锚点 / 链接、`children` 顺序、`text` 字节、图片元数据、
  `meta`；
- 字体身份：`FontSet` 里每个字体的 family / weight / style / 字节长度 + 前 64 字节；
- 页面约束：`page` / `margin` / `writing_mode`；
- 调用方的 `policy_rev`。

这个选择让缓存**没有失效逻辑**：任何一个会改变排版结果的字节变了，键就变了，
旧条目自然不再命中。反过来，只要键相同，输出就必须逐字节相同——这正是
[§2.3 确定性](design.md#23-确定性与编解码)那条不变量的另一面。

几个细节是刻意的：

- 所有 f32 按 `to_bits` 参与哈希，`-0.0` 与 `0.0` 不会被当成同一个值。
- 字体只取前 64 字节：足够区分不同字体文件，又不会为了键把几十 MB 重新哈希。
- 哈希是 FNV-1a。缓存是 caller-owned，键不落盘、不跨信任边界；这里不需要
  密码学哈希，碰撞的后果只是一次错误命中。
- 缓存键与缓存条目都不进 `LayoutResult`：IR 是 native/wasm 的字节契约，一旦
  带上缓存状态，golden 与 parity 就会依赖进程历史。
- 字体身份由调用方 `set_fonts` 显式登记，因为 `LayoutEnv` 只暴露 `TextMeasurer`。
  这是当前形状下的取舍：不改 `LayoutEnv` 的契约，代价是调用方要多一步。

## 11.5 版式档案：机制不认识语言

排版机制（断行、分页、弹性调整）与**语言知识**分开，语言知识全部是数据：

```
StyledDoc.meta.lang ──> typography::of_lang ──> &'static Typography
                                                   ├─ punct: PunctTable   （字符类、可压/可悬集合、比例）
                                                   └─ page:  PageRules    （孤寡修复手段的优先级）
```

- 现在有两份：`GENERIC`（零语言假设，等价于“浏览器默认”）与 `ZH_HANS`（简体中文，CLREQ）。
- 表是 `&'static`：无分配、`no_std` 友好、可穷举测试，也不给第三方插件留后门（那会把确定性卖出去）。
- **验收标准**：新增一门语言只加一个 `static`，不改 `flow.rs` / `paginate.rs` / `punct.rs`。
- `TextRules` 仍是 `ComputedStyle` 上的元素级开关（IR 字节不变）；档案只决定“这个开关打开时用哪张表、宽度多少”。
- 分页的修复手段是**有序数据**：`GENERIC` 是 `[PullUp, MoveWhole]`（与引入档案之前一致），`ZH_HANS` 按 CLREQ §7.1.2 是 `[PushOut, PullUp, MoveWhole]`——孤行首选“挪到上一页、突出版心”。
- 档案还决定**分页怎么决定**（`PageRules::plan`）：`Greedy`（排满一页再回头看）或
  `Optimal`（页级 DP，见 §16），以及 `Optimal` 用的那张代价权重表。换算法不改
  一行分页代码，只换这个字段——和换标点表一样。
- 档案还能改两件**初始值**：块上没有显式 `text-align` 时用谁（中文正文 = `justify`，即 CLREQ §6.2.2 的均排），以及行末标点能不能压到半宽（§6.3.2.3）。两者都只影响声明式默认值，作者写了 `text-align: left` 就不会被覆盖。
- 突出版心的页会把自己的 `Page.size.h` 加高几行，而不是让行落在页盒外：不变量“每行都在页盒内”保持成立，宿主不需要为个别页面写特例。

## 12. 并发只在一次调用内

`Layout::layout_parallel(doc, env, c, workers, opts)` 的并行范围只有**一次调用**：

- `std::thread::scope` 在调用内建线程，任务完成后 join，返回前所有线程都已结束。
- 没有线程池、没有全局队列、没有 `OnceLock` / `lazy_static` / `thread_local`。
- 每个任务只写自己的结果槽；拼回按输入下标，不按完成顺序。
- `workers` 只是本次调用的上限，不是全局配置。
- wasm 关掉 `parallel` feature，`layout_parallel` 直接走串行路径，签名不变，
  输出逐字节相同。

这四条合起来保证：并行结果与串行结果**逐字节相同**。如果并行改变输出，那就说明
有共享状态或非确定顺序，parity/golden 会立刻抓到。

当前并行的是“item → 分页单元”的纯函数映射，不是段落断行本身。真正的段落级
并行需要先在 `flow` 里把断行拆成可独立的任务（计划/断行/回填三段），这属于
排版内核的改动，不在硬化轮次里。

## 13. IR 1.2–1.5 的字段为什么这么放

IR 是位置编码，字段顺序就是字节布局。1.2–1.5 的新字段都遵守同一条规则：
**只在结构体末尾追加**，让旧快照只多出一个后缀，而不是整段错位。

| 字段 | 放在哪 | 为什么不是别的放法 |
|---|---|---|
| `Glyph.ch` | `Glyph` 内部 | 命中与选区需要“每个字形对应原文哪个字节”。放进 `Glyph` 让字形数组仍然是唯一的坐标流；如果另开 `Vec<u32>` 映射，两个数组的切片就必须永远同步，任何一处筛字形都要改两处。 |
| `Op::Link` | `DisplayList.ops` 的一种 op | 链接是渲染/命中关心的事，不是排版几何。放进 op 数组就能跟着 `Page.ops` 一起切片；如果挂到 `LineBox` 上，就得给页再加一个“链接切片”，页覆盖不变量会多一条。 |
| `Issue` | `LayoutResult.issues` | 诊断不能混进 op，否则渲染层要认识“只记录不画”的变体。独立一个 `Vec` 让渲染完全不受影响，`IssueCode` 以后加变体也只动这一个枚举。 |
| `truncated` | `LayoutResult` 最后一个字段（`bool`） | `bool` 在 postcard 里是 1 字节，追加在末尾对旧 golden 的影响最小（每个文件 +1 字节）；放在结构体中间会让后面所有字段错位，等同于 major 变更。 |
| `GlyphRun.weight` / `style` / `underline` | `GlyphRun` 最后一个字段之后 | 文字样式必须跟着 run 走，不能只靠 FontBook：没装字体时 font id 全是 0，宿主仍要知道“这句是 bold / italic / underline”。追加在 `rotate` 之后，旧字段偏移不变。 |
| `TextStyle.underline` | `TextStyle` 最后一个字段之后 | 装饰线先只支持下划线；`line-through` / `overline` 还需要更多字段，等有真实需求再加。 |
| `Limits` | **不进 IR** | 限额是输入，不是输出。写进 IR 会让同一份文档在不同预算下产生不同字节，golden 无法稳定。 |
| `LayoutStats` | **不进 IR** | 它是 `size_of` + 容量 + 字符串长度的估算，用于诊断与预算；一旦序列化，分配器的容量差异会变成字节差异。 |
| `DirtyBlock` | 保持独立 | 增量重排要的是“哪块需要重来”，与 op/行都不是一一对应；保留独立数组才能在不改 IR 其余部分的前提下扩展原因。 |

代价是 `LayoutResult` 的字段顺序从此不能重排；收益是每次加字段都只需要同步
`web/decode.js` / `web/encode.js`，而不必重写所有 golden 与像素基线。

## 13.5 取舍与不做

- 只做横排。`WritingMode` 字段保留，纵向布局不在本轮。
- 只实现成对可判定的 UAX #14 规则；需要上下文的规则明确不装。
- 不做 flex / grid、浏览器级 CSS 兼容、DOM 直渲。
- 不做 PDF、DRM。
- 滚动与分页共用同一份断行/块布局：`Mode::Scroll` 把整章排成一页，
  `paint_window` 按内容 y 取瓦片（窗口外的 op 不画、不查字形）；分页仍是默认模型。
- 跨章滚动不是宿主的事：`scroll_begin` 起的会话给出章节起点、全书总高、
  跨章可见带与流坐标命中，宿主只管“滚动容器 + 把位图贴上去”。
- 全书高度是**估计 + 实测**两层：`scroll_begin` 不排任何章，实测按章懒发生，
  Fenwick 前缀和 O(log n) 更新；总高允许随实测收敛，绝对位置用锚点保持稳定。
- 章节流（在线书源）不要求整本字节：`append_chapter` / `replace_chapter` 只
  影响该章的 IR 与高度，`chapter_rev` 是宿主页缓存的键。
- 位置分两层：`Anchor`（章 + DOM 路径 + 字节偏移）是稳定位置，`Location`
  （页 + 行 + 字节）只是当前排版的投影。宿主持久化前者，`Locator` 是它的
  C 友好投影（章 + 节点 id + 偏移）。
- 块是排版的二等公民：`LayoutResult.blocks` 记录每个块节点的矩形、行数与
  首行锚点；`LayoutOptions::window` 只排指定块区间，窗口坐标归一化到 0。
  窗口外的块不整形、不产生 op，所以 IR 大小只跟窗口有关。
- 不引 criterion；bench 用 `std::time::Instant`，输出可 diff 的
  `name<TAB>ns`，见 [scripts/bench.sh](../scripts/bench.sh)。

## 14. 行内调整：一张表，两个方向

行内每一处「可以变宽也可以变窄」的位置记一条 `StretchSlot { glyph, space }`：
词距还是字缝是**数据结构的一部分**，不是事后靠字符码猜。同一张表服务两个方向：

- **拉伸**（`justify_line`）：按 `Justify` 分档摊余量；
- **收缩**（`shrink_line`）：按档案给的容量上限等比收紧（见 §17）。

`Justify::Tiered`（CLREQ §6.2.2.4）的顺序是：

1. **西文词距**第一档，但每处最多半个字宽（`0.5em`）——不封顶就会出现一行中间
   一个大洞的「天坑」。
2. **字间隙**兜底，不限量、同级均摊（CLREQ §6.3.1.2 均排）。
3. 整行只有词距、没有字缝可兜底时（纯西文行），退回**整行均摊**：封顶只会把
   余量全塞进最后一处词距，比均摊更难看。

`Justify::Flat` 是引入分档之前的做法（有词距就全摊词距、否则平摊字缝），
`GENERIC` 用它，纯西文文档的字节输出据此与引入分档之前完全一致（像素基线守住）。

> 这里踩过一个坑，值得记下来：分档刚做出来时 `stretch` 表里**只装词距**（有词距
> 就丢掉字缝），于是「有词距且 `slots.len() == spaces`」恒成立，第二档永远是死
> 代码——分档从没生效过，而测试全绿。把两个方向并成一张表之后它才真的跑起来。

## 15. 尺子：怎么判断「变好了」

golden 只说明「变了」，像素基线只说明「没打算改的地方没变」。要判断一次排版改动
是不是让它更像一本书，需要数字。`crates/ebook-layout/src/quality.rs`（feature
`quality`，默认关闭）就是这把尺子：

```sh
cargo run -p xtask -- report              # 三个 fixture + 一本合成长书
cargo run -p xtask -- report 某本书.epub  # 只看这一本
```

```
书                    档案        页   行  齐平  短行  悬挂  挤压   缺口p95   拉伸p95  空洞页  空行  突出  孤行  孤字
fixtures/demo.epub     generic     1   11    36%   64%    0     0     27.13      0.73      0     0     0     0     2
fixtures/demo.epub     zh-hans     1   11    36%   64%    0     0     26.03      1.83      0     0     0     0     0
<合成长书>              generic    62 1315    77%   23%    0     0     24.67      0.67     17    18    11     3    14
<合成长书>              zh-hans    62 1311    77%   23%    0    65     24.67      0.67      0     5     8     0     0
```

同一本书、同一版面、只换 `lang`，两行就是可比的两个档案。

**为什么需要那本「合成长书」**：现有 fixture 只有 11–52 行，而且大半是段末行，
页底空洞、孤字这些列要么恒为 0，要么纯属噪声。`synthetic_book()` 用固定种子的
LCG 造一本 300 段、3.7 万字、60 多页的中文书稿（每次逐字节相同）。

真书更能说明问题。《光之子》（2.9 万行、1441 页，先转成 UTF-8——引擎的 TXT
入口只认 UTF-8，GBK 会被替换成 U+FFFD）：

```
                   页    行   齐平  挤压  拉伸p95  空洞页  空行  突出  孤行  孤字
generic          1441 29129   59%    0    1.15    535   575   429   103   426
zh 贪心 + 齐平    1453 28922   59% 1152    0.67      8   129   233     0   142
zh DP + 齐平      1434 28922   59% 1152    0.67      1   102   319     2   142
```

三行对三行读：

- 页底空洞（`空洞页`）从 535 降到 1。这一项主要靠 §16.1 的齐平——它把零头摊进
  段间距，所以「对齐」和「省纸」不再打架。
- 省纸（`页`）靠 DP：同样开着齐平，贪心 1453 页，DP 1434 页，差 19 页。
- 孤寡（`孤行`）贪心是 0、DP 是 2：贪心靠「整段推走」把寡行硬压下去，代价就是
  那多出来的 19 页。这是一笔明账，不是巧合。
- 孤字 142 是孤字修复没覆盖到的部分（`can_break` 太保守），归第 6 项之后处理。

### 15.1 每个数怎么来的

| 列 | 定义 | 单位 |
| --- | --- | --- |
| 齐平 / 短行 | 行右边缘是否落在版心右缘（页面内容区右缘）±1px | 行数 |
| 悬挂 | 行右边缘探出版心右缘 | 行数 |
| 挤压 | 行末字形的实际 `dx` 比整形宽度少 > ¼ em（标点压半宽） | 行数 |
| 缺口 | 版心右缘 − 行右边缘 | 字（`em`） |
| 拉伸 | `Σdx − Σ整形宽度`：这一行被拉开了多少 | 字（`em`） |
| 空洞页 / 空行 | 页底到最后一行的距离 ≥ ½ 行（不含末页）的页数 / 这些空白折成多少行 | 页 / 行 |
| 突出 | 内容越过版心最后一条格线（版心对齐后本不该被用到的那一截） | 页数 |
| 孤行 | 跨页孤寡：下一页页首挂着上一段最后一行，或页尾只剩下一段第一行 | 处 |
| 孤字 | 段末只剩 1 字、或 1 字 + 标点 | 段数 |


「拉伸」是唯一必须重新算一遍的量：IR 里的 `dx` 是**拉伸之后**的值，所以尺子用
`TextMeasurer::shape` 把每行的 run 重新整形，和 IR 比差值。没有字体也能跑
（`StubMeasurer` 的整形就是逐字前进宽度），所以它和 golden 用同一套几何。

### 15.2 刻意不猜的东西

- **段落边界**。行盒里没有段落 id，靠 y 相邻去猜会被代码块、表格、引用骗到
  （一行 12 字、下一行 60 字，看起来完全像同一段的一个烂断行）。所以「齐平率」
  的分母是**所有**行，含段末行和缩进的块——它是一眼观感的下界，只看横向比较。
  这也是为什么不报「平均缺口」而报 `p95`：少数段末行会把均值拖走。
- **绝对好坏**。`齐平 33%` 不代表排版差，可能只是这本书短段落多。尺子只回答
  「同一本书换一个档案 / 换一个算法，数字朝哪边动」。
- **哪一页真的"浪费"了**。`空行` 量的是「从最后一行底部到版心底」的白，其中可能
  只是一段段间距（`margin-bottom`），任何一行都放不进去。所以它只用来横向比较
  同一本书的两个档案，不是"这本书浪费了 N 行纸"的绝对值。纸的绝对值看页数。

## 16. 页级 DP：一次决定所有切点

贪心分页是「排满一页，再回头看页尾丑不丑」——它只看得到当前这一页，所以每修一次
页尾，空洞就往下推一页。改动越多，结论越乱：在《光之子》上，只加孤寡修复和版心
对齐，页底空白从 381 行涨到 658 行；把 `PushOut` 拿掉更差（1031 行）。这不是某条
规则错了，是**逐页决策本身没有全局视野**。

页级 DP 换个问法：把「单元 `s..e` 算一页」看成一条边，边上记这页的代价，求从
`0` 到 `n` 的最短路径：

```
best[0] = 0
best[e] = min over s of best[s] + cost(s, e)      cost 见下
```

一页装得下几十个单元，所以每个起点只往后开一个窗口，总代价 `O(n × 每页单元数)`；
《光之子》29129 个单元排完不到一秒。

**`cost(s, e)` 是取舍，不是规则**：

| 项 | 含义 |
| --- | --- |
| `slack²` | 页底空掉 n 行：平方是因为十页各空一行比一页空十行好看 |
| `over_base + over·n²` | 让这页多放 n 行、探出版心 |
| `widow` / `orphan` | 段末孤行落在下一页页首 / 段首孤行留在页尾 |
| `split` | 段落中间断页（中文几乎不介意，给一个很小的数只为在平局时偏向段界） |
| `avoid` | 违反了 `break-inside: avoid`。软约束，但很贵 |

这张表是 `PageRules::cost`（`PageCost::ZH`），和标点表一样是**数据**。中文的取舍
来自 CLREQ §7.1.2：宁可让一行探出版心，也不要孤行——所以 `over` 定得比 `widow`
低，DP 才会优先用「多放一行」而不是「往回挪一行」来消灭孤行（挪一行要在页底留
一条白，多放一行不用）。

**为什么行高要单独传进来**：`cost` 里的"一行"必须是正文行高。如果按"这一页最后
那个单元的高度"量，页尾放一张大图会把一行撑成 100px，窗口和代价一起失准。所以
`paginate::body_line()` 取全书出现次数最多的那一档行高，`plan()` 显式收它；
`align_lines` 的版心对齐也用同一个数。

**确定性**：代价是 `f32`，平局按"先到先得"（`cost < best[e]` 严格小于，`s` 递增
遍历）——同一本书在 native 和 wasm 上切点逐字节一致，有测试盯着。

**`Greedy` 必须留着**：`GENERIC` 档案走它，golden 与像素基线才不用动。两个档案
共享同一套 `Unit` 流、同一个 `PageBuilder`，差别只有 `PageRules::plan` 一个字段。

### 16.1 页底齐平：把零头摊进段间距

版心对齐行高之后，页面高度除不尽行高，会剩一条零头（《光之子》：752 − 23×31.5 =
27px）。这条零头只有三种去处：

| 去处 | 代价 |
| --- | --- |
| 留白（纯对齐） | 每页浪费小半行，1400 页累计 47 页纸 |
| 硬塞一行（`push_lines`） | 页底参差不齐，22% 的页差一行 |
| **摊进段间距**（LaTeX `\flushbottom`） | 无——段间距本来就有弹性 |

第三种的实现是 `paginate::flush_scale()`：给每页算一个拉伸比例，组装时把每个
**空隙**乘以它、把后面的内容整体下推。两条硬约束：

- **只动空隙，不动行距**。行距是设计出来的，拉它等于改版式；段间距不是。
- **每道缝最多撑 0.1 行（约 3px），而且至少要有两道缝**。这条上限不是为了几何，
  是为了**观感**：渲染出来看过，同一页的段间距从 10px 撑到 30px，翻过去一眼就
  是「这页怎么这么松」。撑到 13px 则看不出来。所以撑不下就别撑——页底留一条白，
  比把整页的段间距改掉更像书。

实测（同一套分页切点，只开/关这一项）：

```
每道缝上限        页    空洞页   空行   最松那页的段间距
关（不对齐）    1434    600    598    —
半行（15.8px）  1434      1    102   30.3px  ← 太松，一眼看得出
0.1 行（3.2px） 1434     99    200   ~13px    ← 收下的这版
```

页数一个没变。收严之后有 99 页（7%）撑不满、页底留一条白——那些正是「页里段落
太少，撑了会变松」的页，留白是对的。有背景/边框的页也跳过不摊（装饰 op 按块算，
跟着字一起挪就得知道它挂在哪一段上，不知道就宁可这一页不齐）。

想看就自己看：`cargo run -p xtask -- render 某本书.epub 12 出图.bmp zh`，页号写
`worst` 会挑段间距被撑得最开的那一页。

### 16.2 怎么避免把权重调成「只对一本书好」

`PageCost::ZH` 的六个比例是在《光之子》（2.9 万行、长段落、TXT）上量出来的，
所以它必须过两道检验，不能只在那本书上看着好：

1. **留出书**。手边另有 10 本没参与调参的 EPUB，取三本跑同一套权重：
   页数与贪心**完全相同**（51 / 28 / 41），页底空白持平，跨页孤寡 1→0、3→0、
   孤字 37→13、13→2、34→13。也就是说在短段落书上 DP 是「不亏、略好」，
   机制没帮倒忙；「少 19 页」只发生在长段落书上，因为它本来就是贪心更能作践
   的那类书（贪心一次撤一整段）。
2. **扰动**。把六个权重同时乘 0.25 / 4，结果**一字不变**——代价是齐次的，
   只有相对大小有意义，这本身就是一道保险。单独把「孤寡」乘 0.25 / 4，页数
   1434 / 1436，纹丝不动。唯一敏感的是「突出版心」的权重：乘 4 会让页数从
   1434 涨到 1457（比贪心还差），因为那等于禁止 DP 用版心余量。所以这个数
   往下调才安全，`PageCost::ZH` 取的是便宜那一侧。

结论要写在明处：**机制（一次性挑切点）不是针对某本书的；六个权重是经验值，
它们能忍多大幅度的扰动，上面两个检验给了边界。** 再调这些数时，同样要留出
一本书不看。

## 17. 行内：压缩容量、压行、行级 DP

页级 DP 解决的是「在哪切页」，切点之间的**每一行**还是贪心断出来的。这一段补上行
内的两件事：给每个字缝一个收紧上限，以及整段一起挑断点。

### 17.1 压缩容量：谁都可以变窄一点

`LineRules::gap_shrink` / `space_shrink`（单位 em）是档案数据：中文 0.05 / 0.1，
generic 全是 0（不压）。容量按缝隙数算，所以长行的余量大、短行几乎没有——这和纸书
的观感一致：行越长，收紧一处越看不出来。

有了容量，`shrink_line` 就能把一行收进版心：按每处自己的容量等比例收，收完各行
一样紧。只在**需要腾一个位置**时用（孤字的那种「压行」），常态仍然是拉伸。

### 17.2 孤字：两条路，先便宜后贵

CLREQ §7.1.2。段落末行只剩一个字（或「字 + 标点」）时：

1. **往下挪**——从上一行取一整块下来。关键在「一整块」：只挪一个字时，如果上一行
   末尾是标点，挪下来的就是标点，末行以标点开头，违反避头尾，于是什么都不做。
   改成从最近的**合法断点**往回找，挪下来的常常是「字 + 标点」两个字。
2. **压行**——往回挪不动（拉丁文一长串没有断点、末行又非挪不可）时，把整个末行
   收进上一行，靠 §17.1 的容量腾位置。

《光之子》上：不修 213 个孤字，两条路一起上剩 0 个。留出书 `book01`：3 → 1，
`book03`：0 → 0，`book02`：0 → 0。

顺带修了两个不显眼的 bug，两个都会让孤字永远修不掉：

- 段落**以换行结尾**时，末行是在换行分支里产出的，而孤字修复只挂在「文件末尾
  没换行」那条路上——TXT 的段落几乎都以换行结尾，等于全书漏检。
- 分类表漏了 `！`（U+FF01）和 `？`（U+FF1F）。孤字判定查的是**标点分类表**，
  `……呢！` 这种末行于是永远不算孤字。悬挂表里有这两个字，分类表里没有——两张
  表各写各的就会这样。

### 17.3 行级 DP（Knuth–Plass）

一段文字里的断点一次挑完：

```
best[0] = 0
best[j] = min over i of best[i] + demerits(i, j)
demerits = (10 + badness)² + hyphen² + orphan
badness  = 100 · |ratio|³      ratio = 余量 / 容量（收不下就不可行）
```

几个实现上必须钉住的点：

- **最后一行单独处理**：段末行是散行，可以短（`badness = 0`），但不许超宽、不许
  悬挂——没人给它收边。它靠挤压才放得下时，挤压要在**交付之前**真的施加到字形上，
  否则 DP 以为放得下、画出来却探出版心（第一版就这么错了 229 行）。
- **窗口**：自然宽度超过版心 1.5 倍就不必再看更长的行，代价 O(n × 每行字数)。
- **不可行有两种**：收不下（`ratio < -1`）、拉不开（只有一个字，没有缝）。少了后者，
  「一行只放一个字」会因为「没有缝可摊」被算成零代价，DP 会主动制造枯行。
- **`LinePlan::Greedy` 必须留着**：`GENERIC` 走它，golden 与像素基线才不用动。

**实测：中文正文上 DP 与贪心等价。**《光之子》同一个档案，只切 `plan`：

```
              页    行   挤压  空洞页 空行 孤行 孤字
Greedy       1434 28922 1089   99   200   2   0
Optimal      1434 28922 1092   99   200   2   0
```

原因不神秘：中文每行都能靠均排填满，一行「差多少」分摊到三四十道字缝之后就看不见
了，于是所有行的 `badness` 都趋近 0，DP 退化成「行数最少」，而「行数最少」就是
贪心。**中文真正消灭孤字的是 §17.2 的两条路，不是 DP。**

DP 的收益在西文和混排上（词距有真实代价）。把 `generic` 临时切成 `Optimal`，拿一份
41KB 的重排英文（`/usr/share/common-licenses` 合并成整段）量：

```
            页   行  齐平  短行  拉伸p95
Greedy      36  768  79%  21%   4.43em
Optimal     36  768  79%  21%   3.95em   ← 行尾松紧更匀
```

页数行数不变，最松的那些行收紧了 11%。这也是为什么 `ZH_HANS` 开着它、`GENERIC`
关着：它不花钱，混排的书（中文书里的英文术语、代码注释）用得上。

### 17.4 尺子也跟着改

「孤字」这一栏除了报数，还得说清**哪些不该记**：

- `……` 独占一行不是孤字——两个字都是标点，那是标点自己落到了一行，另一种毛病；
- 一整段只有一个字（「◇」场景分隔、编号「1」）也不是排版弄出来的。

记上这两类，账就永远平不了，而且会引导后面的人去「修」一个本来不该动的东西。
`quality::is_single_line_para` 和 `is_orphan` 的 2 字形分支就是干这个的。

还剩一类尺子分不清的：一个大号装饰字自己占一行（《book01》里那个 46px 宽的字形）。
它一个字形成行、确实"孤"，但那是版式设计，不是断行的后果。宁可在账上留这 1 笔，
也不去加"字形特别宽就不算孤字"这种规则——尺子的每一条判据都得能对每本书讲清。
